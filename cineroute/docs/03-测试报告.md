### 2.1 这些用例测的是什么

不是"代码没崩"，是**检测能力**。举两个例子：

- **取证**：构造器可以精确指定"第 600 秒起插入 20 秒、码率 3 倍、GOP 0.5 秒的内容"，
  然后断言检测器在**那个位置**报出发现、置信度达标、两项证据都命中。
- **下载器**：对着一个真实的本地 HTTP 服务下载，验证分块偏移写对、断点续传只补未完成的块、
  校验和不匹配时不交付成品。这些用 mock 验证等于没验证。

### 4.1 一个值得记的事

第一次跑时"MP4 干净（单次 x264 编码）"标记为失败，因为我预期是 `suspicious`。
查下来是**我的预期写错了，不是代码错了**：单次 x264 编码、moov 在 mdat 之后、
没有编辑列表、单条视频轨、keyint 与实测 GOP 吻合——确实没有任何可疑点，判 `clean` 是正确的。
改掉预期后 8/8。

这条记下来是因为：一个不会误报的取证工具，比一个"什么都报可疑"的工具有用得多。

## 7. 没测到的（重要）

这一节是这份报告里最该看的部分。

### 7.1 完全没有被任何测试加载的文件

| 文件 | 作用 | 现状 |
|---|---|---|
| `src/web/app.js` | 前端全部逻辑 | **从未在浏览器里运行过**。Chromium 在本沙箱起不来（exit 144），只做了 `node --check` 语法检查 |
| `src/server/server.js` | HTTP 服务 | 无单元测试。接口行为靠 §5 的手工 curl 验证 |
| `index.js` | 检索 CLI | 无单元测试，靠手工运行验证 |
| `forensics.js` | 取证 CLI | 同上 |
| `src/forensics/ffmpeg.js` | ffmpeg 进程调用 | **本环境无可用 ffmpeg**（只有 Playwright 自带的 `--disable-everything` 构建，无 H.264 解码器），这段代码一行都没执行过 |

### 7.2 测试用的是合成文件，不是真视频

所有取证用例都跑在**程序生成的容器**上——MP4 的 `mdat`、fMP4 的分片数据都是占位字节，
MKV 里是填充数据。**没有一个真实的 H.264 码流经过测试**。

这意味着：容器解析、样本表还原、统计判据都验证过了，但如果真实文件里存在
我没预料到的结构（罕见的盒排列、lacing、B 帧重排序、多 trun、非标准封装），
可能会出问题。**上真实样本前建议先拿十来个已知来源的文件对一遍。**

### 7.3 像素层只验证了算法，没验证调用

`frames.js` 里的 pHash（DCT + 中位数阈值）、逐像素时间方差、连通域检测，
都用合成帧数据测过，结果正确。但**从帧数据是怎么来的**——即 ffmpeg 的
spawn 调用、参数、裸灰度流的切分——完全没执行过。

### 7.4 真实网络从未打通

archive.org、TMDB、Wikimedia 在本环境被出口策略拦截（CONNECT 403）。
适配器的解析逻辑用**真实形状**的响应夹具测过，但没有对过一次真实上游响应。
上游若改了字段名或结构，测试不会发现。

### 7.5 规模与性能没测

最大测试样本 5.1 MB。真实场景是 2–20 GB 的影片：

- MP4 的 `moov` 在长片里能到几十 MB，`parseStts` 会把游程展开成逐样本数组——
  一部 3 小时 60fps 的片子是 65 万个样本，内存占用没实测过
- MKV 要整文件扫描，2 GB 文件的实际耗时没测过
- 分块下载器只对着本地服务下过 1 MB

### 7.6 覆盖率里的低分项

- **`jellyfin.js` 行覆盖 26%、函数覆盖 0%**——只测了"缺配置时跳过"，
  真正的检索、直链拼装、字段映射一行没测。这是覆盖率表里最该补的一格。
- `tmdb.js` 分支 26.67%、`internetArchive.js` 分支 37.70%、
  `wikimediaCommons.js` 分支 31.03%——都只测了成功路径，
  错误响应、空结果、字段缺失等分支没走到。
- `fragments.js` 分支 43.10%——`tfhd`/`trun` 的标志位有十几种组合，
  只测了最常见的一种。真实世界的封装器会用别的组合。

## 8. 建议的补测顺序

按性价比排：

1. **拿真实样本对一遍**（§7.2）——最可能暴露问题，成本最低，找十来个已知来源的
   MP4/MKV 跑一下就行
2. **`jellyfin.js` 补单测**（§7.6）——覆盖率表里唯一的明显空洞
3. **HTTP 服务补集成测试**（§7.1）——把 §5、§6 的手工 curl 固化成用例，
   否则每次改动都要手工重跑
4. **前端跑一次真实浏览器**（§7.1）——本沙箱做不到，需要在能起 Chromium 的环境做
5. **适配器错误路径补测**（§7.6）——上游 500、空结果、字段缺失
6. **大文件压测**（§7.5）——等有真实样本之后一起做
