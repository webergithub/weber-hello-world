# 主流视频监控平台接入能力调研（2026-08）

> 目标：回答「米家小米摄像头、360 摄像机等，到底能不能拿到视频流、怎么拿」，并给出一套
> 能同时接入多家平台的统一方案。结论先行：**没有任何一个 SDK 能通吃所有平台**，工程上正确的做法是
> **分平台适配 → 统一归一化成一条 RTSP/HLS 流 → 上层（分析、剪影、推送）只面对归一化后的流**。
> 本项目 `watchtower/` 就是按这个结论实现的。

---

## 一、四条接入路径

任何一款监控设备，能不能被第三方系统拉到流，取决于它属于下面哪一类：

| 路径 | 说明 | 典型平台 | 稳定性 | 是否需要商务/资质 |
| --- | --- | --- | --- | --- |
| **A. 厂商云开放平台 OpenAPI** | 官方文档化接口，服务端换取带时效的播放地址 | 萤石(海康)、乐橙(大华)、涂鸦 | ⭐⭐⭐⭐⭐ | 注册开发者即可，部分需企业认证 |
| **B. 设备本地标准协议** | ONVIF Profile S 发现 + RTSP 直接拉流 | 海康/大华/宇视商用机、TP-Link VIGI、雄迈系 | ⭐⭐⭐⭐⭐ | 不需要 |
| **C. 私有 P2P 协议桥接** | 社区实现的协议栈，本地把私有流转成 RTSP | **小米/米家**、Tapo、Wyze、Ring、Nest | ⭐⭐⭐ | 不需要，但随固件升级可能失效 |
| **D. 国标 GB/T 28181 级联** | 作为上级平台接入已有 NVR / 安防平台 | 各家安防平台、政企项目 | ⭐⭐⭐⭐ | 需对方平台配合开通 |

**没有第 E 类**——即"一个官方 SDK 同时接入米家和 360"的东西不存在。市面上宣称"全平台接入"的产品
（EasyNVR / 大牛直播 / Frigate / Scrypted 等），内部同样是这四类路径的组合。

## 二、逐平台结论

### 2.1 小米 / 米家 ⭐ 重点

| 项 | 结论 |
| --- | --- |
| 官方云 OpenAPI 出流 | **没有**。小米 IoT 开发者平台（iot.mi.com）主要面向生态链硬件厂商做设备接入；2023 年起对个人开发者开放内测，但**未提供面向第三方的摄像头视频流 OpenAPI** |
| 原生 ONVIF / RTSP | 绝大多数机型**不支持**；少数新机型/新固件开始放开 RTSP，购买前必须确认**具体型号 + 地区 + 固件版本** |
| 可行方案 ① | **go2rtc 内置 `xiaomi://` 源**（推荐）：直接走小米 P2P 协议本地拉流，支持双向语音 |
| 可行方案 ② | **Micam**（`github.com/miiot/micam`）：基于小米官方 **Miloco** + go2rtc 的 RTSP 桥接服务，Docker Compose 部署，无需 GPU，可接 HA / Frigate / Scrypted / HomeKit |
| 可行方案 ③ | 刷第三方固件（yi-hack 系）拿原生 RTSP —— **会失去保修、有变砖风险，不推荐生产使用** |

go2rtc 的小米源语法（本项目 `adapters/xiaomi.py` 生成的就是这个）：

```
xiaomi://<小米账号UID>:<区域>@<摄像头局域网IP>?did=<设备ID>&model=<型号>&subtype=hd
# 例：xiaomi://1234567890:cn@192.168.1.123?did=9876543210&model=isa.camera.hlc7
# subtype: auto/sd/hd 或 0-5（0=自动 1=标清 2=高清，go2rtc 默认 2）
```

两个必须知道的坑：

1. **每次建连仍需公网**：小米 P2P 的加密密钥要向小米云换取，所以"纯离线局域网"跑不通，
   断网后已建立的流可以继续，但重连会失败。
2. `did` / `model` / `UID` 要从米家账号里导出（Micam、Xiaomi MIoT Auto 等工具都提供导出）。

> **一句话**：小米走「**本地桥接 → RTSP**」，不要等官方云 API。

### 2.2 360 智能摄像机

| 项 | 结论 |
| --- | --- |
| 官方开放平台 | 有 —— **360 智能摄像机开放平台**（dev.jia.360.cn），提供 Android / iOS / JS SDK + 服务端 API，可脱离 360 账号体系、用户与设备权限由开发者自管 |
| 能否服务端直接拉流 | **不能**。开放平台的视频能力集中在**客户端 SDK**里；服务端 API 主要做设备/用户/告警管理 |
| ONVIF / RTSP | **不支持**，也没有可用的第三方固件 |
| 可行方案 ① | 走开放平台商务申请，拿 SDK 做**客户端播放**；服务端侧只拿事件与设备状态 |
| 可行方案 ② | **端侧转推旁路**：一台常驻安卓设备跑 SDK 播放 + 推 RTMP 回本系统。工程可行但重，适合确实必须纳管 360 的场景 |
| 可行方案 ③ | 若该机型支持"NVR/网络存储/局域网直连"等新特性，按 B 类当普通 RTSP 接 |

> **一句话**：360 是本次调研里**最封闭**的一家。本项目为它保留 `qihoo360` 适配器，实现为
> 「开放平台事件接入 + 手工/旁路流地址」的组合，并在配置里显式标注 `stream_via=manual|relay`，
> 避免给用户"点一下就能拉流"的错觉。

### 2.3 萤石 EZVIZ（海康民用）⭐ 最容易接入

标准 OpenAPI，本项目一等公民：

```http
POST https://open.ys7.com/api/lapp/token/get
     appKey, appSecret                      → accessToken（有效期 7 天，需定期刷新）

POST https://open.ys7.com/api/lapp/v2/live/address/get
     accessToken, deviceSerial, channelNo,
     protocol, quality, expireTime, type    → 播放地址
```

- `protocol`：`1`=ezopen `2`=hls `3`=rtmp `4`=flv
- **H.265 设备只能走 ezopen**（要用萤石播放器/SDK）；HLS / RTMP / FLV **仅支持 H.264**
- 播放地址**有有效期**（`expireTime`），且有防盗链，必须服务端按需申请、过期重取
- 想让分析流水线也能用，**设备编码要设成 H.264**，否则只能拿 ezopen，服务端解不了

### 2.4 乐橙 Imou（大华民用）⭐ 一等公民

统一 POST 网关 `https://openapi.lechange.cn/openapi/<method>`，请求体带
`system.sign = MD5("time:<time>,nonce:<nonce>,appSecret:<secret>")`：

```
accessToken            → 拿 token
bindDeviceLive         → 为设备建立直播通道
getLiveStreamInfo      → 拿 HLS / RTMP / RTSP 播放地址
unbindLive             → 释放通道（重要，通道数有配额）
```

RTMP 直播协议于 2021 年上线，HLS / RTSP 同期可用。注意 `bindDeviceLive` 是**有配额的资源**，
用完必须 `unbindLive`，否则很快耗尽。

### 2.5 涂鸦 Tuya（覆盖大量白牌 / 贴牌 IPC）⭐ 一等公民

覆盖面最广的一家——很多不知名品牌的摄像头其实是涂鸦方案，接了涂鸦就等于接了一大片：

```http
POST /v1.0/token?grant_type=1                              → access_token
POST /v1.0/devices/{device_id}/stream/actions/allocate
     {"type": "rtsp"}   # 或 "hls"                          → 播放地址
```

签名为 HMAC-SHA256（`client_id + access_token + t + nonce + stringToSign`）。
**返回的地址有效期很短（通常几分钟）**，必须"随取随用"，不能缓存进配置。

### 2.6 其余平台速查

| 平台 | 路径 | 接法 |
| --- | --- | --- |
| TP-Link Tapo | C | go2rtc `tapo://user:pass@ip`（支持双向语音） |
| TP-Link VIGI | B | 原生 ONVIF/RTSP，或 go2rtc `vigi://` |
| 海康 / 大华 / 宇视 商用 | B | `rtsp://user:pass@ip:554/...` 直连，ONVIF 自动发现 |
| Ring / Nest / Wyze | C | go2rtc `ring://` `nest://` `wyze://` |
| Apple HomeKit 摄像头 | C | go2rtc `homekit://` |
| 已有 Frigate / Home Assistant | — | 直接把它的 restream RTSP 当上游，或 go2rtc `hass://` |
| 安防平台 / NVR | D | GB/T 28181 级联，本系统作为上级平台 |

## 三、统一归一层：为什么选 go2rtc

调研过的候选：**go2rtc** / MediaMTX / ZLMediaKit / EasyNVR / Frigate。

选 **go2rtc** 的理由：

1. **它本身就是"多平台适配器集合"**——内置 rtsp、rtmp、onvif、hls、mjpeg、ffmpeg、以及
   **xiaomi、tuya、tapo、vigi、kasa、ring、nest、wyze、homekit、doorbird、hass** 等私有协议源。
   本次调研里 C 类平台的绝大部分它已经替我们做完了。
2. **输出侧一次搞定所有播放端**：

   | 用途 | 地址 |
   | --- | --- |
   | 低延迟播放（App/浏览器，约 0.5s） | `http://<go2rtc>:1984/api/webrtc?src=<name>` |
   | 兼容播放（MSE/fMP4，`<video>` 直接播） | `http://<go2rtc>:1984/api/stream.mp4?src=<name>` |
   | iOS Safari / 兜底 | `http://<go2rtc>:1984/api/stream.m3u8?src=<name>` |
   | 分析抽帧 / 缩略图 | `http://<go2rtc>:1984/api/frame.jpeg?src=<name>` |
   | 给 ffmpeg / NVR 拉 | `rtsp://<go2rtc>:8554/<name>` |

3. **一路上游、多路下游**：摄像头只被拉一次，直播、录制、分析共用，省带宽也省设备并发配额
   （萤石/乐橙的并发是要钱的）。
4. 资源占用低，树莓派可跑，无 GPU 要求。

因此本系统的分工是：

```
各平台适配器（拿到一条能播的 URL）
        ↓  写入 go2rtc streams 配置 / REST 动态加流
      go2rtc（归一化 + 分发）
        ↓
   ┌────┴────┬──────────┐
 直播播放   分析流水线   录制/剪影
```

## 四、服务端分析选型

| 环节 | 选型 | 备注 |
| --- | --- | --- |
| 抽帧 | go2rtc `frame.jpeg` 轮询 / ffmpeg 管道 | 轮询实现最简单、对流最友好，本项目默认 |
| 一级筛选 | 帧差 + 背景建模（MOG2） | 无人时不喂模型，CPU 占用降一个数量级 |
| 人形检测 | **YOLO26**（Ultralytics，2026-01）优先；ONNXRuntime / OpenCV HOG 兜底 | YOLO26 默认 NMS-free、对小目标更友好，适合监控画面里的远处人形 |
| 跟踪 | ByteTrack（单摄像头够用）/ BoT-SORT（带轻量 ReID） | 本项目内置零依赖 IoU 跟踪器作为默认，重依赖可选 |
| 跨摄像头 ReID | OSNet / TransReID | **默认关闭**，仅在明确需要"同一个人跨镜头串联"时开 |
| 人脸 | InsightFace | **默认关闭**，涉合规，见 `04-合规与隐私.md` |
| 部署 | 导出 ONNX，走 ONNXRuntime / TensorRT / OpenVINO | 比原生 PyTorch 推理快 2–3 倍且不绑训练栈 |

**分级设计**：本项目把检测器做成可插拔的三档，装什么用什么，最低档零第三方依赖也能跑通全流程
（见 `server/watchtower/analysis/detectors.py`）：

```
yolo（ultralytics）  >  onnx（onnxruntime）  >  motion（opencv 帧差）  >  stub（无依赖，仅供测试）
```

## 五、合规红线（必读）

中国大陆部署必须注意这两部 2025 年生效的法规，细节见 [`04-合规与隐私.md`](04-合规与隐私.md)：

- **《公共安全视频图像信息系统管理条例》**（国务院令第 799 号，2025-04-01 施行，共 34 条）：
  公共安全视频系统采集的图像信息**保存不少于 30 日**；用于公开传播且可能损害他人权益的，
  须对人脸、车牌等敏感信息做严格保护（打码/脱敏）。
- **《人脸识别技术应用安全管理办法》**（网信办 + 公安部，2025-06-01 施行）：
  人脸信息应当**存储于人脸识别设备内、不得通过互联网对外传输**；须取得**单独同意**；
  有其他验证方式的不得把人脸作为唯一验证方式；**宾馆客房、公共浴室、更衣室、卫生间等私密空间内禁止安装**。

对本项目的直接影响，已落到代码里：

1. 人脸识别默认 `face.enabled = false`，且人脸特征只允许落本地库，不进推送、不出公网。
2. 一日剪影与推送默认走 `privacy.blur_faces` 打码开关。
3. 事件与录像有 `retention_days` 保留策略（默认 30 天，可上调）。
4. 仅面向**自有场所、自有设备**；接入他人平台账号需取得授权。

## 六、给本项目的最终选型结论

| 平台 | 采用路径 | 本项目适配器 |
| --- | --- | --- |
| 小米 / 米家 | C：go2rtc `xiaomi://` 或 Micam 桥接 | `adapters/xiaomi.py` |
| 360 | 手工/旁路 + 开放平台事件 | `adapters/qihoo360.py` |
| 萤石 EZVIZ | A：官方 OpenAPI | `adapters/ezviz.py` |
| 乐橙 Imou | A：官方 OpenAPI | `adapters/imou.py` |
| 涂鸦 Tuya | A：官方 OpenAPI | `adapters/tuya.py` |
| 海康/大华/宇视/VIGI/杂牌 | B：ONVIF + RTSP | `adapters/onvif_rtsp.py` |
| 任意已知 URL / go2rtc 原生源 | 直通 | `adapters/generic.py` |

新增一个平台 = 写一个实现 `resolve()` 的类并注册，**上层一行不用改**。
