## 分层职责

| 层 | 目录 | 只做一件事 |
| --- | --- | --- |
| 适配 | `adapters/` | 各平台 → 一条可播 URL（`resolve()`） |
| 归一 | `media/streams.py` `media/go2rtc.py` | 把 URL 注册进 go2rtc；**盯住短效地址自动续期** |
| 录制 | `media/recorder.py` | 每路一个 ffmpeg 常驻分段录制，挂了按退避重启 |
| 分析 | `analysis/` | 抽帧 → 检测 → 跟踪 → 事件；纯计算，可单测 |
| 剪影 | `digest/` | 选段 → 合成 → 文案 |
| 推送 | `push/` | 分数门槛 / 聚合窗口 / 免打扰 → 各通道 |
| 接口 | `api/` | REST + SSE + 受控媒体读取 |

**依赖是单向的**：上层依赖下层，下层不知道上层存在。所以换掉任何一层（比如把 go2rtc 换成
MediaMTX、把 IoU 跟踪换成 BoT-SORT）都不用动其它层。

## 几个关键决策

### 1. 为什么常态录制，而不是"检测到人再录"

**事件发生前的几秒才是最有价值的**——人是从哪来的、怎么进来的。等检测到人再启动录制，
前情已经丢了。所以持续切 10 秒小段，事件结束后再从段里裁出带 `pre_roll` 前摇的片段，
全程 `-c copy` 不重编码。

### 2. 为什么分析从 go2rtc 抽帧，而不是自己连摄像头

摄像头（尤其云平台）**并发路数是有限的，而且要钱**。直播、录制、分析各连一次，
三倍消耗还容易触发平台限制。走 go2rtc 就只拉一次。

### 3. 为什么先做运动检测再喂模型

监控画面 95% 的时间没有任何变化。先用 MOG2 背景建模过一遍，没动静的帧根本不进模型，
CPU 能降一个数量级。这也是 `detector=motion` 能作为兜底档单独使用的原因。

### 4. 为什么事件要"开得迟疑、关得有耐心"

- 开：连续 `open_frames` 帧命中才开事件 → 滤掉单帧误检（飞虫、光斑）。
- 关：连续 `close_seconds` 秒没人才关 → 避免一个人被树挡两秒就被切成两条事件。

事件**起点回溯到第一次命中的那一帧**，而不是"确认开事件"的那一帧——否则
`open_frames` 有几帧，事件前面就丢几帧，恰好丢掉人进画面的过程。

### 5. 为什么推送要三道闸门

监控系统最常见的失败不是漏推，是**推太多以致于没人看**。所以：分数门槛 →
同摄像头聚合窗口 → 免打扰时段。一日剪影**不受免打扰限制**（它本来就是回头看的东西）。

### 6. 短效地址是多平台聚合最大的坑

涂鸦的播放地址几分钟就失效，萤石按 `expireTime` 过期。地址写死进配置，第二天全黑屏。
`StreamManager.refresh_expiring()` 每 30 秒检查一次，提前 60 秒续期并热更新 go2rtc；
**从没解析成功过的摄像头也在这里重试**，等于自带故障自愈。

## 数据模型

```
cameras  ──< events ──> clips/thumbs（文件）
             │
             └──> digests（按天，含 stats.clips 章节信息）
subscribers ──< push_log
kv          （各平台 accessToken 缓存，带 TTL）
```

SQLite + WAL，每线程一个连接。单机十几路摄像头、一天几千条事件，这个量级 SQLite 绰绰有余；
真到几十上百路再换 PostgreSQL，DAL 层接口不用变。

## 扩展点

| 想做什么 | 改哪里 |
| --- | --- |
| 接一个新平台 | 写一个 `CameraAdapter` 子类 + 在 `adapters/__init__.py` 注册 |
| 换更强的检测模型 | `analysis/detectors.py` 加一个 `Detector` 实现 |
| 跨摄像头认人（ReID） | 在 `analysis/` 加 ReID，事件 `meta` 里带 `person_key` |
| 换推送通道 | `push/channels.py` 加一个 `Channel` |
| 改剪影风格（竖版/带音乐） | `digest/renderer.py`，`orientation` 已支持竖版 |
| 换存储后端 | `db.py` 的 `Database` 类，接口保持不变 |
