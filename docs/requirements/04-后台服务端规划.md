## 1. 为什么现在需要服务端（触发本规划的硬事实）

本规划**不是**"加个后端比较完整"，而是由一条经代码核实的品类硬伤触发。

### 1.1 核实到的事实

| # | 事实 | 证据 |
|---|---|---|
| S#1 | 产品承诺的核心场景是"**车队路上**互相跟车不走散"，画像写明"自驾车队组织者…路上在地图上看各车位置" | `docs/requirements/01-需求规格说明书.md:41,47` |
| S#2 | 原生端位置共享**只经 BLE**：`ConvoyFragment.kt:171` 与 iOS 同构，均为 `MeshBus.send(kindLoc)` | 代码走读 |
| S#3 | BLE 有效距离**约 10 米**（项目自己的文档如此记载并写入真机测试前提） | `02-需求规划文档.md:136`、`docs/REAL-DEVICE-TEST.md:23,105,109` |
| S#4 | 原生端**完全没有网络传输代码**：grep `URLSession`/`NSURLConnection`/`HttpURLConnection`/`OkHttp`/`WebSocket` 在 `ios12/Sources`、`android-native/**` 均**零命中** | grep 核实 |
| S#5 | Android 声明了 `INTERNET` 权限但从未使用——**残留声明** | `AndroidManifest.xml:4` 对比 S#4 |
| S#6 | Web 端有网络能力（`WebRTCTransport` + 信令服务器），**原生端没有**；二者能力不对称 | `src/lib/transport.ts:80,139` |
| S#7 | 现有信令服务端仅 124 行，只转发 SDP/ICE，**不承载业务数据** | `server/signaling.js` |

### 1.2 由此得出的差距（新增 Gap）

> **G-NET-1（L1 品类硬伤）**：高速/国道行驶时车距通常 50–200 米，远超 BLE 的约 10 米。
> 因此在**原生 App** 上，"跟车"只在堵车挪动、服务区停车、停车场集合等**贴近场景**成立；
> 一旦真正"在路上跑起来"，同伴标记会先变淡再消失（G-DR-2 的掉线逻辑如实反映了链路真相），
> **旗舰功能的核心场景不成立**。

这与 G-CM-1（营地语音曾"宣称>实现"）同级，但影响面更大：营地是"没信号时的加分项"，
而跟车是**产品名字的由来**（TrailMate / 出游助手的第一个 tab）。

### 1.3 与既有非目标的冲突（显式改判）

②§12 曾记载："**账号体系/云同步：当前不做（保持零后端、隐私优先）；仅做本地导出**"。

- **当时的判断依据**：把"零后端"视为隐私优先的设计选择。
- **遗漏**：未意识到零后端使 T1「路上不走散」在原生端**任务前提不成立**（S#1–S#4）。
- **本规划的改判**：非目标从"不做后端"收窄为"**不做账号体系、不做明文云存储**"；
  **哑中继（只转发密文）不属于非目标**，因为它不引入账号、不引入明文、不改变隐私立场（见 §3）。
- 保留的非目标：注册/登录账号、服务端可读的明文业务数据、长期轨迹留存（默认关）。

## 2. 任务导向复核（D1）：服务端到底服务哪个任务

沿用 ② 的 JTBD 方法，逐任务判断"是否需要服务端"，避免为了做而做。

| 任务 | 成功条件 | 现状 | 需要服务端？ |
|---|---|---|---|
| T1 路上不走散 | 车距 50–200m 仍能互见位置 | ❌ BLE 约 10m（G-NET-1） | ✅ **必需**——物理上 BLE 无解 |
| T1 路上不走散 | 喊话对方听得到 | ⚠️ 原生对讲仅 BLE 距离 | ✅ 必需（同上） |
| T2 无信号也能联络 | 营地无蜂窝时互通 | ✅ BLE mesh 已满足 | ❌ **不需要**——此场景恰恰没网，服务端无用武之地 |
| T3 花销算得清 | 各家账目能合并成一本 | ⚠️ 各设备各记各的，无合并 | ⚠️ 可选——也可用"导出/导入"或近距 BLE 同步兜底 |
| T3 花销算得清 | 账目不会因换机/卸载丢失 | ⚠️ 仅手动备份（G-LG-1） | ⚠️ 可选——云备份是便利，非前提 |

**结论**：服务端的**唯一刚需**是 T1（跟车距离）；T2 明确不需要（保持 BLE 优先）；T3 属于便利性增强，排在后面。
这条结论直接决定了下面的优先级：**先做位置/消息中继，别一上来做账号和云同步**。

## 3. 架构原则：哑中继（Dumb Relay）

### 3.1 关键洞察：加密已经做完了，中继几乎是"免费"的

E1 阶段已落地端到端加密（G-CM-3）：MeshBus 载荷为
`AES-256-CBC + HMAC-SHA256`，密钥由**队伍码**经 `PBKDF2-HMAC-SHA256(salt=trailmate-mesh-v1, 10000)` 派生，
服务端**不掌握队伍码**，因此：

> **服务端转发的是密文，永远看不到聊天内容与位置坐标。**
> 它只看得见"某个队伍房间里有帧在流动"。

这意味着引入服务端**不需要**削弱 C-3「零信任中继」原则——恰恰相反，它是 C-3 的自然延伸：
原本的信令服务器就已经是"只牵线不看内容"，现在只是把同样的哲学用到业务帧上。

### 3.2 双通道并行，而非二选一

| 通道 | 适用 | 成本 |
|---|---|---|
| BLE mesh | 近距（营地、停车场）、**无网可用** | 零流量、零服务器 |
| 网络中继 | 远距（行车途中）、跨城 | 少量流量 + 服务器 |

**两条通道同时开，不做"优先级切换"**——理由：`msgId` 去重机制（`BleMesh` 已有，`seen` 集合）
天然处理"同一条消息从两条路都到达"的情况，重复帧会被静默丢弃。
因此并行是**最简且最鲁棒**的选择：无网时自动只剩 BLE 生效，有网时两条路互为冗余。

> 这一点很重要：它意味着**不需要写复杂的链路选择/切换状态机**，
> 也不会出现"切换瞬间丢消息"的经典缺陷。

### 3.3 网络帧：绝不原样发送 MeshBus 帧（v1.0 初稿的重大更正）

> ⚠️ **本节是实现时发现并更正的设计缺陷。** 初稿写的是"帧格式不变，服务端按 `team` 字段分房转发"——
> 但 MeshBus 信封里的 `team` 是**明文**，而 `team` 恰恰是 PBKDF2 派生密钥的**唯一输入**。
> 照初稿实现，服务端拿到队伍码即可自行派生密钥解密一切，"哑中继"当场破功。
> **队伍码绝不上传服务端。**

改用**房间哈希**路由，并做域分离：

> `roomId = SHA256("trailmate-room-v1|" + 队伍码)` 的十六进制。
> 盐 `trailmate-room-v1` 与加密派生用的 `trailmate-mesh-v1` **不同**，
> 因此即便房间哈希泄漏，也无法反推或复用为解密密钥。

网络协议（客户端 ↔ 服务端）：

> 入房：`{type:'relay-join', room, token}`
> 转发：`{type:'relay', room, kind, body}`，body = base64(端到端密文)

- 服务端看得见：**房间哈希、kind 字节、密文长度**。看不见：队伍码、消息内容、坐标。
- 收端用**自己的队伍码**解密 body；MAC 不过即丢（同时天然处理哈希碰撞）。
- `kind` 留在密文外仅为路由便利，属**已知的极小元数据泄漏**（服务端能区分"位置帧"与"聊天帧"，但不知内容）；
  如需消除，可将 kind 移入密文，代价是收端需先解密才能路由。
- 必须先 `relay-join`（含 token 校验）才能 `relay`，否则任何知道房间哈希的连接都能无凭据注入帧
  （**此校验在实现初稿中曾被遗漏，已由夹具第 12 组断言锁定**）。

## 4. 需求清单（BR 编号）

### 4.1 S1 阶段 · 位置与消息中继（P0，对应 G-NET-1）

| 编号 | 需求 | 破坏性验收 |
|---|---|---|
| BR-1.1 | 原生 iOS/Android 新增网络传输层（WebSocket），与 BLE 并行收发同一套 MeshBus 帧 | 两台手机相距 >1 公里（超 BLE 范围）、均有蜂窝网络：地图上必须能互见位置，标记不得变淡消失 |
| BR-1.2 | 服务端按**房间哈希**分房转发密文（队伍码绝不上传，见 §3.3），不落业务明文 | 服务端日志/存储中检索队伍码明文与消息正文，必须**零命中**；抓取转发流量不可还原明文 |
| BR-1.3 | 双通道去重：同一 `msgId` 经 BLE 与网络双至时只处理一次 | 两机同时处于 BLE 范围内且都联网，互发 10 条消息，两端各自只显示 10 条（无重复） |
| BR-1.4 | 断网/服务端不可达时静默降级为纯 BLE，不得阻塞 UI、不得反复弹错 | 飞行模式下（仅开蓝牙）营地与跟车必须与今日行为完全一致；连接失败不得出现循环弹窗 |
| BR-1.5 | 链路状态如实可见：分别显示"蓝牙 N 台 / 云端 M 台"，不得把"云端在线"伪装成"蓝牙邻居" | 关蓝牙但保持联网：状态必须显示蓝牙不可用、云端仍在线；反之亦然 |
| BR-1.6 | 网络中继沿用 `SIGNAL_TOKEN` 同款鉴权 + 限流（复用 G-SEC-1 成果） | 错 token 连接被拒；高频灌注被限流断开 |

### 4.2 S2 阶段 · 离线补投与提醒（P1）

| 编号 | 需求 | 破坏性验收 |
|---|---|---|
| BR-2.1 | 存储转发：成员离线时，其队伍的密文帧在服务端暂存，上线后补投（**默认保留 24 小时，到期删除**） | 甲发消息时乙断网；乙 24h 内上线必须收到；超 24h 后上线必须收不到（且服务端已删除） |
| BR-2.2 | 暂存亦为密文，且带容量上限（每队伍 ≤2 MB，超限丢最旧） | 灌注 5 MB 后检查：服务端占用不超过上限，最旧帧已被淘汰 |
| BR-2.3 | 后台提醒（iOS APNs / Android FCM 或轮询降级） | — 见 §6 风险：iOS 推送需付费账号；老安卓可能无 GMS。**本项依赖决策 D-3** |

### 4.3 S3 阶段 · 账目多设备合并（P2，对应 G-LG-1 增强）

| 编号 | 需求 | 破坏性验收 |
|---|---|---|
| BR-3.1 | 账目条目经中继同步，按 `expenseId` 去重合并（同一队伍内） | 甲乙各记 3 笔后互联：两端都必须显示 6 笔，且结算净额、转账笔数完全一致 |
| BR-3.2 | 合并冲突策略：同 id 以 `ts` 较新者胜；删除用墓碑标记 | 甲改金额、乙删同一笔，同步后两端状态必须一致（不得一端有一端无） |
| BR-3.3 | 同步同样走密文，服务端不可读账目 | 服务端存储中检索金额/项目名，零命中 |

### 4.4 明确不做（继续列为非目标）

- **账号注册/登录**：继续用「队伍码 + 设备 ID」，零注册。加账号会引入密码找回、隐私政策、合规负担，与产品调性不符。
- **服务端可读的明文业务数据**：任何阶段都不做。
- **长期轨迹留存/回放**：默认不做（隐私）；若将来做，必须显式开关 + 本地存储优先。
- **实时视频中继**：仍为非目标（②§12），与带宽无关，是产品边界选择。

## 5. 技术方案与选型

### 5.1 服务端形态（在现有 124 行信令服务上生长）

现有 `server/signaling.js` 已具备：WebSocket 房间管理、token 鉴权、限流、大小上限、单 IP 上限。
**S1 只需增加一个"业务帧中继"消息类型**，复用全部现有防护，预计增量 **< 100 行**。

> WebSocket（Android）：`{type:'relay-join', room, token}` / `{type:'relay', room, kind, body}`
> HTTP 长轮询（iOS 12，决策 D-2 已定）：`POST /relay/join` → `{sid}`、`POST /relay/send`、`GET /relay/poll?sid=`
> 两种传输在服务端落入**同一房间集合**（成员=投递器抽象），故 Android ↔ iOS 跨传输互通。

### 5.2 部署方案对比（**决策点 D-1**）

| 方案 | 月成本 | 运维 | 适合 |
|---|---|---|---|
| **A. 单台小 VPS**（1核1G + Caddy 自动 HTTPS） | ￥20–40 | 需自己更新/续费/看监控 | 推荐起步：几十个队伍绰绰有余 |
| B. Cloudflare Workers + Durable Objects | 免费额度内约￥0 | 免运维、全球加速 | 需改写为 Workers 风格（WebSocket API 不同） |
| C. Fly.io / Railway 容器 | ￥0–40 | 中等 | 直接跑现有 Node 代码 |

**推荐 A 或 C**（现有 Node 代码可直接部署，改动最小）；B 性能与成本最优但需重写服务端。

### 5.3 客户端改动量估计

| 端 | 改动 | 量级 |
|---|---|---|
| Android | 新增 `NetTransport.kt`（OkHttp WebSocket 或原生），接入 MeshBus 双通道 | 中（~200 行） |
| iOS 12 | 新增 `NetTransport.swift`；⚠️ iOS 12 **无原生 URLSessionWebSocketTask**（iOS 13+ 才有），需手写 WebSocket 帧或用 `Starscream` | 中偏大（~300 行或引入依赖，**与"零第三方依赖"约束冲突，见决策点 D-2**） |
| MeshBus | 抽象出「传输通道」概念，BLE 与 Net 同为通道，收发都过同一去重 | 小（~50 行 ×2 端） |
| 服务端 | 增加 relay 类型 | 小（<100 行） |

## 6. 依赖与风险（跨条目联动）

| 风险 | 影响 | 缓解 |
|---|---|---|
| **iOS 12 无内建 WebSocket API** | 若坚持"零第三方依赖"（`project.yml` 现状），需手写 RFC 6455 帧解析 | 备选：改用**长轮询 HTTPS**（`URLSession` iOS 12 可用，实现简单得多，位置 3 秒一报本就不需要长连接）——**推荐** |
| **服务端 = 单点故障 + 持续成本** | 服务器挂了会不会影响现有功能？ | BR-1.4 已规定：必须静默降级为纯 BLE，即"服务端挂掉 = 回到今天的产品"，不会更差 |
| **推送依赖付费账号**（与 G-ENG-3 同源） | iOS APNs 需付费开发者账号；老安卓无 GMS 时 FCM 不可达 | S2 的 BR-2.3 单独隔离，不阻塞 S1；可先用"打开 App 即补投"替代推送 |
| **流量与电量** | 位置 3 秒一报，长连接耗电 | 行车时本就充电；可加"仅在跟车页开启网络通道"策略 |
| **隐私观感** | 用户可能担心"位置传到了服务器" | 需在 UI 与文档明说：**服务器只见密文，解密密钥由队伍码派生且从不上传**；并提供"仅蓝牙"开关 |
