# CityTwin 后端演进规划 · 以「真在线多人对战」为主线

> 版本 V1.0 ｜ 基线提交 `d450b83` ｜ 目标：让异地好友真正一起玩 n 人躲、m 人找
>
> 本文的事实部分均已对照 `game.js`（4951 行）逐条核实并标注行号，不是推测。

---

## 1. 执行摘要

**推荐架构**：**服务端权威 + 轻量实时（Authoritative-Lite）**——从第一天就把胜负相关裁决放到服务端（不写日后要推倒的临时同步），但利用 CityTwin「**没有战斗系统 + 人类躲藏者提交后静止**」这两个已核实的特性，**跳过客户端预测与回滚重演**这类 FPS 才需要的重型 netcode。

**为什么这是关键判断**：常规多人游戏的 netcode 成本大头在「打中没打中」的延迟补偿。CityTwin 里 `hp` 全是 `headPos`(车头位置)，全代码无 damage/health/shoot（已核实）；实时竞争性交互只有三个**离散的接近事件**——抓捕 3.2m（`game.js:3422`）、物资 2.4m（`2661`）、空投 2.8m（`2710`），全部延迟容忍。因此：

- 其他寻找者的位置晚 100ms 到达 → **纯观感问题，不影响公平**，标准插值即可；
- 三个离散事件 → **服务端 RPC 裁决**，客户端等回包即可；
- 人类躲藏者提交后完全静止（`updateHiders:3205`，逃窜逻辑 `3224` 明确限定 `!h.isHuman`）→ 躲藏者根本不需要位置同步，只需要**服务端保守秘密**。

这把方案 B 估算中最贵的 60 小时（预测+回滚+和解）基本省掉。

**分四期**，每期独立上线、独立产生价值：

| 期 | 目标 | 工期（每周 8–12h） | 上线后玩家能感知到什么 |
|---|---|---|---|
| **P0** | 地基与止血 | 1–1.5 周 | 照片级 3D 城市**首次真正可用**（无需自备 key） |
| **P1** | 身份与战绩上云 | 1.5–2 周 | 换设备不丢形象/生涯，有排行榜和每日挑战 |
| **P2** | 一对一化重构 | 2–3 周 | 玩家无感（但这是多人的唯一入场券） |
| **P3** | 实时联机对局 | 4–6 周 | **异地好友真正一起玩** |

**首个联机对局约在第 9–13 周**（每周 8–12 小时）。作为对照：方案 B 的全量权威路线要 3.5–7 个月且中途零用户价值；本方案靠 P0/P1 在第 2 周就开始兑现价值。

**最先做的三件事**：① 修部署管线（已完成，见 §2.3）；② Google Tiles 服务端托管 + 硬熔断；③ 把 `G.credits`/`player` 一对一化。

## 2. 现状核实（全部对照代码，非推测）

### 2.1 阻挡多人的三个结构性事实

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| ① | **信用点是全场唯一钱包** | `G.credits` 全局单值：初始化 `4240`，扣费 `3413`，收入 `2637/2666/2714/3525` | m 个寻找者在线时无法各自计费 |
| ② | **全场只有一具身体** | 全文件仅一个 `const player = {}`；`G.seekers[]` 结构为 `{name,captures,earned}`（`4248`），**无位置、无钱包、无体力** | 现在的「m 人找」其实是**一个人的 75 秒接力赛**，不是多人 |
| ③ | **客户端完全权威且有直通后门** | `window.__hs = { G, player, capture: captureHider, ... }`（`4946`）；`captureHider`（`3515`）零校验 | 控制台一行即可通关；联机下必须服务端裁决 |

> ①② 是**热座模式的遗留假设**。它们不是"顺便重构"，而是多人功能的**唯一入场券**——所以 P2 独立成期。

### 2.2 降低 netcode 难度的两个有利事实

| 事实 | 证据 | 价值 |
|---|---|---|
| **无战斗系统** | 全文 `damage/health/shoot/weapon` 零命中；8 处 `hp` 均为 `headPos` | 免去命中判定、延迟补偿、回滚重演 |
| **人类躲藏者静止** | `createHider:3165` 产出静止 mesh；逃窜仅 `!h.isHuman`（`3224`） | 躲藏者零位置同步；断线容错难度低一个数量级 |
| **世界由 seed 完全决定** | `resetWorld` 设 `G.seed` 后 `rng = mulberry32(seed)`，城市/藏点/物资/空投/天气/AI 布局全部派生 | 车辆、NPC、行人、天气、昼夜**两端各算不同步**，省掉绝大部分带宽 |

### 2.3 已修复：部署管线的两个真 bug

调研发现并经我核实：

1. **`photoreal/` 从未被部署过**——`deploy.yml:62` 的 rsync 清单里没有它。上一轮做的照片级 3D 原型在服务器上根本不存在。**已修复**（清单补入 `photoreal`，`deploy/mac-deploy.sh` 同步修正）。
2. **`rsync --delete` 会删光后端文件**——目标目录中不在清单内的一切都会被删除。若把后端、数据库、`.env` 放进 web root，**每次 push 都会被清空**。**已加注释警告**，并在架构上强制后端放 `/opt/citytwin`（见 §7）。

**另需处理（P0）**：`deploy/deploy-on-server.sh` 已过期且危险——它往 `/etc/nginx/conf.d/` 写独立 server 块，而该目录是与 `duplicate-finder`、`battleai` **共享的爆炸半径**，一个语法错误会让三个站点一起下线；且其中的 `restorecon`(SELinux)/`firewall-cmd`(firewalld) 分支在 Ubuntu 镜像上是**永不触发的死代码**。应废弃或重写。

## 3. 架构决策（ADR）

### ADR-1：采用「服务端权威 + 轻量实时」，而非纯增量或纯重构

- **否决 纯增量（方案 A）**：它把实时同步推到最后一期，且刻意降级为「客户端跑物理、服务端只裁决花钱」。在**用户已明确选择实时多人为首要目标**的前提下，这等于把主线放到最后，且中途的异步玩法可能白做。
- **否决 全量权威（方案 B）**：它要求服务端复现完整物理与城市几何，先付 90 小时把 `genRealCity` 拆成纯数据 `buildCityModel`，首个联机对局要 3.5–7 个月。对个人开发者而言，**半年不出货的风险远大于架构不纯的风险**。
- **采纳 折中**：服务端权威**只覆盖胜负相关的离散裁决**（抓捕/账本/雷达/稀缺资源/计时），移动与世界仿真留在客户端并用**速度上限 + 轨迹连续性**软校验。因为无战斗，这个精度足够。

### ADR-2：服务端不加载 13MB 城市几何

- 服务端只加载**每城约 1.3MB 的碰撞摘要**（AABB + 40m 空间网格），由 `tools/bake-collision.mjs` 从现有 `data/` 离线生成；
- 移动校验用**速度上限 + 位移连续性**（阈值见 §6.2），穿墙检测降级为「抽样点是否落在建筑 AABB 内」；
- 理由：Oracle Always Free 机型（**2026-06-15 已从 4 OCPU/24GB 腰斩到 2 OCPU/12GB**，部署前须 `nproc && free -m` 确认）扛不起完整几何 × 并发房间。

### ADR-3：技术栈 —— Node 22 LTS + `ws` + SQLite，零框架

| 选型 | 决策 | 理由 |
|---|---|---|
| 运行时 | Node 22 LTS，内置 `node:sqlite` | 与游戏同语言可共享校验/常量代码；免原生编译（ARM 机型上 `better-sqlite3` 可能编译十几分钟甚至 OOM） |
| HTTP | 内置 `node:http` + 手写路由 | 端点仅十余个；避免三年后 `npm audit` 里的传递依赖负债 |
| 实时 | `ws`（纯 JS） | 不用 socket.io：体积与每连接内存大一个量级 |
| 存储 | SQLite（WAL）单文件 | 写入是「一局结束写一行」量级；免去 Postgres 的运维负担 |
| 打包 | esbuild | 预编译二进制，无编译步骤 |

### ADR-4：必须保住 `file://` 离线单机可玩

这是现有的珍贵特性（双击 `index.html` 即玩）。模块化改造后，**无后端时游戏必须仍能完整运行单人/热座局**。做法：网络层做成可缺失、可降级的适配层，检测不到后端就走纯本地路径。

## 4. 分期路线图

### P0 · 地基与止血（1–1.5 周）

| 交付物 | 验收标准 |
|---|---|
| 修部署管线（**已完成**：photoreal 入清单、rsync 警告） | push 后服务器上存在 `/citytwin/photoreal/` |
| 废弃/重写 `deploy-on-server.sh`，改用 nginx include 子目录模式 | 改动只落在 CityTwin 自己的 2 个配置文件，`nginx -t` 通过 |
| Google Tiles 代理（P0 先纯 nginx 版）+ 合规归属条 | 玩家**无需填 key** 即可看照片级 3D 城市 |
| `data/` 五个建筑文件改按城市懒加载 | 首屏从 13MB 降到约 2.5MB |
| 生产构建剥掉 `window.__hs` | 生产页面控制台无 `__hs` |

**价值**：照片级 3D 城市第一次对普通玩家可用；首屏流失率大幅下降。

### P1 · 身份与战绩上云（1.5–2 周）

| 交付物 | 验收标准 |
|---|---|
| Node 骨架：`127.0.0.1:8787` + systemd + 真实 `/healthz` | 崩溃自恢复；`MemoryMax` 生效 |
| 匿名身份（服务端签名 token）+ 6 位迁移码 | 换设备后形象/生涯战绩可迁移 |
| Tiles 代理搬进 Node（剥客户端 key、按玩家配额、用量入库、**硬熔断**） | 超限自动降级回开放数据白模，不产生额外账单 |
| 整局摘要上报 + 四类排行榜 + 每日挑战（固定 seed） | 榜按 (城市, 时长, 难度, worldVersion) 分桶 |

**价值**：跨设备同步 + 「和全世界比」，且**零实时同步需求**。

> 埋点务必第一天就存**整局摘要**而非三个计数器——赛季、回放、平衡调参都吃这份数据。

### P2 · 一对一化重构（2–3 周）· 多人的入场券

| 交付物 | 验收标准 |
|---|---|
| `G.credits` → `players[id].credits`；`player` 单例 → `players[id]{pos,yaw,credits,stamina,riding,freeRadar,captures}` | 单人/热座局行为**零变化**（回归测试） |
| 抽出 `shared/`：线索违禁词校验、`COST`、`SPEED`、成就规则、确定性 rng | client/server 共用同一份，Node 里可跑测试 |
| ESM 化 + esbuild 打包，产物路径不变 | `file://` 双击仍可完整玩单人局 |

**价值**：玩家无感，但这是 P3 的唯一前置。**不要试图跳过这一期**。

### P3 · 实时联机对局（4–6 周）

| 交付物 | 验收标准 |
|---|---|
| WebSocket 房间：6 位房间码 + LOBBY/HIDE/SEEK/ENDED 状态机 | 异地好友可创建/加入 |
| 服务端权威：抓捕、账本、雷达、物资、空投、计时 | 控制台改数值无法影响结果 |
| 兴趣管理（AOI）：躲藏者坐标**永不下发**给未发现方 | devtools 里搜不到躲藏者位置 |
| 10–15Hz 位置广播 + 100ms 插值缓冲 | 他人移动平滑无跳变 |
| 90 秒断线宽限 + 全量基线重连 | 掉线重连回到对局 |

**价值**：**异地好友真正一起玩 n 躲 m 找**。

## 5. 多人联机设计

### 5.1 权威划分

| 事项 | 权威方 | 说明 |
|---|---|---|
| 抓捕判定 | **服务端** | RPC，校验距离 ≤3.2m、双方非载具、目标未被抓、请求者是 seeker、冷却 |
| 信用点账本 | **服务端** | 8 个收支口全部改 RPC；每笔带幂等键 |
| 雷达测距 | **服务端** | 只回距离与冷热档，**绝不回方向**（这本是设计意图，须保留） |
| 稀缺资源（16 物资/空投） | **服务端** | 先到先得，服务端裁决 |
| 计时与结束 | **服务端** | 客户端只显示 |
| 移动 | 客户端 + 服务端软校验 | 速度上限 + 轨迹连续性（§6.2） |
| 车辆/NPC/行人/天气/昼夜 | **两端各算，不同步** | 由 seed 确定性派生 |

### 5.2 信息不对称（本作 netcode 的核心）

> 躲猫猫的灵魂是信息不对称。**躲藏者坐标一旦进入寻找者客户端内存，游戏就废了。**
> 现状恰恰相反：`tryRadar:3465` 直接读本地真值算距离——说明客户端本来就持有全部躲藏者坐标。

**分级下发规则**：

| 距离 | 下发内容 |
|---|---|
| > 26m | **什么都不发**（连"这里有人"都不发） |
| 12–26m | 只发**音频提示事件**（窸窣声），不含坐标 |
| ≤ 12m 且视线可达 | 才下发坐标与模型，供渲染 |

- 视线用碰撞摘要做 2D LOS 判定，避免"隔墙看到人"；
- 为避免"贴脸才弹出"的突兀感，进入 12m 时用**淡入**而非瞬显；
- 脚印（`h.tracks`）已有 26m 渐显机制，与此分级天然一致，可直接复用。

### 5.3 带宽估算

4 人房（1 躲 3 找）：

- 上行：每客户端 15Hz × (pos 3×int16 + yaw int16 + flags) ≈ **~0.2 KB/s**
- 下行：每客户端收其他 2 个寻找者位置 15Hz ≈ **~0.4 KB/s**
- 离散事件（抓捕/拾取/雷达）：稀疏，忽略
- **合计每房 < 3 KB/s**，20 房 < 60 KB/s。Oracle Always Free 带宽绰绰有余。

> 躲藏者不动 → 零位置流量。这是本作相对常规联机游戏的巨大优势。

### 5.4 躲藏阶段的防偷看

热座靠"轮流上机+遮屏"，异地多人下重新设计：

- 躲藏阶段各躲藏者**独立并行**选点，服务端只收 `{spotId, clue, bounty}`，互不广播；
- 寻找者在此阶段客户端处于**锁定等待态**（看倒计时与已就位人数，收不到任何位置数据）；
- 服务端权威校验线索违禁词（客户端校验可绕过）。

### 5.5 WebSocket 消息协议（骨架）

| 方向 | 类型 | 载荷 | 频率 |
|---|---|---|---|
| C→S | `HELLO` | `{token, protocolVersion}` | 连接时 |
| S→C | `WELCOME` / `VERSION_MISMATCH` | `{roomState}` / 强制刷新 | 连接时 |
| C→S | `INPUT` | `{tick, x, z, yaw, flags}` | 15Hz |
| S→C | `SNAPSHOT` | `{tick, peers:[{id,x,z,yaw}]}`（**经 AOI 过滤**） | 15Hz |
| C→S | `RPC_CAPTURE` | `{targetHint, clientTick, nonce}` | 事件 |
| C→S | `RPC_SPEND` | `{kind, amount, nonce}` | 事件 |
| C→S | `RPC_RADAR` | `{nonce}` | 事件 |
| S→C | `LEDGER` | `{credits, delta, reason}` | 事件 |
| S→C | `EVENT` | `{kind, payload}`（抓捕/物资/空投/天黑） | 事件 |
| S→C | `PHASE` | `{phase, timeLeft}` | 状态变更 |

`protocolVersion` 必须在 `HELLO` 时严格比对——客户端在浏览器缓存里、服务端在你手上，版本不一致是必然事件，**这条从第一天就要有**。

## 6. 安全与防作弊

### 6.1 作弊手法对照表

| 手法 | 现状 | 对策 |
|---|---|---|
| 控制台直接抓捕 | `__hs.capture()` 可用（`4946`） | 生产剥离 `__hs`；抓捕改服务端 RPC |
| 无限信用点 | `G.credits += n` 客户端执行 | 账本服务端权威，收支全走 RPC + 幂等键 |
| 读取躲藏者位置 | 客户端持有全部坐标 | AOI 分级下发（§5.2） |
| 瞬移/穿墙 | 无校验 | 速度上限 + 轨迹连续性（§6.2） |
| 伪造结算刷榜 | 无校验 | 三条软校验对账（§6.3） |
| 线索绕过违禁词 | 纯客户端校验 | 服务端复用 `shared/` 同一套规则 |

### 6.2 移动合法性阈值（基于已核实常量）

基准 `SPEED = {walk:4.6, run:8.2, bike:11.5, bus:12}`，实际速度 `= 基准 / 3 × SIM.mul`（默认 `mul=3` 即 1.0×）。

- 服务端按玩家当前 `riding` 状态取上限，**乘 1.35 容差**（网络抖动 + 帧率波动）；
- 跳跃期允许瞬时垂直位移（`vy=5.4`，`g=13.5`，`game.js:3651/3654`）；
- 连续 3 个 tick 超限 → 拉回上一合法位置（不封号，静默纠正）；
- 单 tick 位移 > 上限 × 5 → 判定瞬移，记事件并纠正；
- 出租车/地铁是**合法瞬移**，必须走服务端 RPC 授权后才允许坐标跳变。

### 6.3 排行榜防刷（个人项目不必做到完美）

三条软校验挡住绝大多数伪造，不通过则**不入榜、不封号**：

1. 用时 ≥ 理论下限（按藏点间最短路径估算）；
2. `G.stats.dist` 与用时、交通次数自洽；
3. 最终 credits 与「起始额 − 花费 + 抓捕奖励(`COST.captureBase=50` + bounty) + 拾取」对得上账。

## 7. Google 3D Tiles 托管与成本熔断

> **这是把账单风险从玩家转移到你身上的一步，熔断不是可选项。**

**代理设计**：
- 服务端持有唯一 key，客户端永不接触；
- 只放行白名单路径（`createSession`、`3dtiles/*`），拒绝任意透传；
- 短 TTL 性能缓存，**不做长期落盘复制**（遵守 Map Tiles API 条款）；
- 客户端必须保留 Google 归属信息与 logo（合规硬要求）；
- 保留「高级玩家仍可填自己的 key」作为降级路径。

**四层熔断**（缺一不可）：

| 层 | 机制 | 触发后 |
|---|---|---|
| 单用户 | 令牌桶（如 2000 tile/日/设备） | 该用户降级白模 |
| 全局日配额 | 计数入库 + 每日重置 | 全站降级白模 |
| 全局月配额 | 对齐 Google 免费额度的 80% | 全站降级白模 + 告警 |
| GCP 侧 | 在 Google Cloud 控制台设**预算告警 + 配额硬上限** | 最后一道保险 |

> 前三层在你代码里，第四层在 Google 控制台——**必须都设**。只做代码层，一旦服务被刷会直接反映成账单。

## 8. 部署运维要点

- **物理隔离**：静态资源 `/home/ubuntu/website/citytwin/`（rsync `--delete` 管辖区）；后端 `/opt/citytwin/`（**绝不放 web root**）；数据库 `/var/lib/citytwin/citytwin.db`。
- **nginx**：不新增 `server` 块（会与 `duplicate-finder`/`battleai` 抢 `default_server`），改用 include 子目录往既有 server 注入 location；所有 http 级符号（`map`/`limit_req_zone`）加 `ct_` 前缀防撞名；改完强制 `nginx -t && systemctl reload nginx`（reload 而非 restart）。
- **绑定**：后端一律 `127.0.0.1:8787`，永不监听 `0.0.0.0` —— 零防火墙改动、零 VCN 改动、零对外攻击面。
- **systemd**：`Restart=always` + `MemoryMax=300M` + `SIGTERM` 后 20 秒优雅退出（先停新连接、给 WS 发 close 帧）。
- **日志**：journald 限容（`SystemMaxUse=300M`），零维护。
- **健康检查**：`/healthz` 必须探到内部真实状态（房间管理器心跳时间戳、内存占用），不能无脑 `return 200`。
- **CI/CD**：拆两个 job——静态走现有 rsync，后端走 `/opt` + `systemctl restart`。

## 9. 风险登记册

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| P2 一对一化重构失控 | 高 | 中 | 先写「5 城 × 200 seed 输出比对」回归工具再动手；单人局行为零变化是硬验收 |
| Google 账单失控 | 高 | 中 | 四层熔断（§7），第四层设在 GCP 控制台 |
| 躲藏者在线局干坐 6–8 分钟 | 中（劝退） | **高** | 协议第一版就预留 hider→server 主动技能通道（一次转移/假脚印/看一次热力图） |
| 机型内存不足（Always Free 已腰斩） | 中 | 中 | 部署前 `nproc && free -m` 确认；房间数硬上限；`MemoryMax` 关住爆炸半径 |
| 协议版本不一致 | 中 | **高** | `HELLO` 严格比对 `protocolVersion`，不匹配强制刷新 |
| 后端文件被 rsync --delete 删除 | 高 | 中 | 架构上强制后端在 `/opt`（已加注释警告） |
| 没有用户时后端是纯成本 | 中 | 中 | 单进程 + SQLite，闲时near-零成本；保留纯前端单机可玩 |

## 10. 本轮不做什么（防范围蔓延）

- ❌ **密码/邮箱账号体系** —— 匿名 token + 迁移码即可；密码找回与邮件服务是长期负债
- ❌ **服务端 AI 躲藏者** —— 第一版只做真人躲真人找；AI 逐帧逃窜是服务端 tick 成本最高的一块
- ❌ **回放与观战** —— 需要事件流全量落库，等对局数据模型稳定后再说
- ❌ **UGC 自定义城市** —— 烘焙管线尚未产品化
- ❌ **服务端完整物理与 13MB 几何** —— 见 ADR-2
- ❌ **客户端预测与回滚重演** —— 无战斗系统，不需要（本方案最大的成本节省项）
