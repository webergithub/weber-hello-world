# 影视集中搜索平台 · 调研洞察

> 版本 v1.0 · 对应实现：`cineroute/`
> 一句话：原始设想里「多引擎爬全网 → 解析播放按钮 → 抓视频直链 → Top5 直播 + 离线下载」的技术路径既跑不通也不合法；
> 但拆掉这层壳之后，**用户真正要的四件事有三件半可以完整、合法地交付**，本文说明是哪三件半、以及怎么做。

## 0. 结论先行

| 原始设想的能力 | 判定 | 本方案的交付形态 |
|---|---|---|
| 一次输入片名，多源并发检索 | ✅ 完整交付 | 4 个适配器并发，单源失败不拖垮整体 |
| 逐个"打开"结果做深度解析，识别真实视频文件地址 | ✅ 完整交付，但**换了解析对象** | 不靠爬 HTML 猜播放按钮，而是解析归档站的结构化文件清单，拿到含 md5/时长/分辨率的真直链 |
| 给出 Top5 播放地址，点开即播 | ✅ 完整交付 | 六维可解释打分 + 两趟排名 + 真实探测，`<video>` 直连播放 |
| 选中片源离线下载 | ✅ 完整交付 | Range 分块并发 + 断点续传 + md5/sha1 校验 |
| 覆盖**任意**院线新片 / 在播剧集 | ❌ 不做 | 受版权保护的作品只给正版观看渠道（JustWatch 数据），不解析播放地址 |

**"半件"落在最后一行**：能力本身全都做出来了，覆盖面被限制在公有领域、自由许可与用户自有媒体库。
这不是能力缩水，是把能力指向了合法的内容集合——下一节说明为什么另一条路根本不存在。

## 1. 原始技术路径的可行性判定

### 1.1 设想的流水线

```
输入片名 → 多个搜索引擎检索 → 逐个打开结果页 → 分析 DOM 找播放按钮
        → 提取视频文件地址 → 排 Top5 → 直接播放 / 离线下载
```

四个环节逐一判定。

### 1.2 环节一：搜索引擎层 —— 可做但昂贵且脆弱

Google / Bing 均无面向此用途的免费官方检索 API（Bing Web Search API 已于 2025 年 8 月停止对外服务）。
现实选项只剩三类：付费检索 API（Serper、SerpAPI 等，按次计费）、自建爬虫（要处理验证码、指纹检测、IP 轮换）、
或改用**垂直数据源的官方 API**。

前两类不仅成本高，而且是一场持续的军备竞赛：结果页 DOM 每变一次，解析器就得重写一次。
第三类才是工程上正确的方向——这也是本方案的选择：**不去爬"搜索结果"，直接对接掌握结构化数据的上游**。

### 1.3 环节二：页面解析层 —— 这是整条路径真正的断点

"找播放按钮、提取视频文件地址"这个假设，停留在 2010 年前后的网页视频形态。视频分发技术已经过三代演进：

| 代际 | 形态 | 能否解析出可用直链 |
|---|---|---|
| 一代（~2012 前） | `<video src="movie.mp4">` 或 Flash 里的 mp4 地址 | ✅ 能，且这正是原始设想成立的年代 |
| 二代（2013–2018） | HLS/DASH 自适应码流，`.m3u8` + 数千个 `.ts` 分片 | ⚠️ 拿到的是清单文件，需重新拼装；且清单地址通常带时效签名 |
| 三代（2018 至今） | EME + DRM（Widevine / FairPlay / PlayReady），密钥经许可服务器下发 | ❌ 拿到的是加密分片，无密钥则是一堆随机字节 |

现今任何一家正规流媒体平台（Netflix、Disney+、爱奇艺、腾讯视频、Prime Video）都在第三代。
它们的播放地址具备以下特征，逐条否定"抓下来就能播"的假设：

- **一次性签名**：URL 带 `expires` + HMAC，通常几分钟到几小时失效，且绑定签发时的会话；
- **绑定 Referer / Origin / Cookie / UA**：脱离原页面请求直接 403；
- **CORS 白名单**：浏览器里跨源 `<video>` 加载被拦；
- **DRM 加密**：即使拿到分片，没有许可服务器下发的密钥也解不开。

所以"抓到的能播的裸直链"在今天几乎必然指向一个事实：**该资源本身就是未授权的盗版副本**——
因为只有盗版站才会把无 DRM、无签名的完整片源裸挂在公网上。技术上的"能抓到"和法律上的"不该抓"在这里是同一件事。

### 1.4 环节三、四：播放与下载层 —— 法律上的一票否决

即便绕过上述所有技术障碍，产品形态本身构成对版权作品的**规模化定位、传播与复制协助**：

- 深链聚合并提供播放：在多数司法辖区构成帮助侵权（contributory infringement）；
- 提供离线下载：直接构成对复制权的侵害协助；
- 中国《著作权法》第十条（复制权、信息网络传播权）、第五十三条；美国 DMCA §1201（规避技术措施）与 §512 避风港的排除情形，均已覆盖。

行业先例明确：Popcorn Time、Showbox、以及众多"影视聚合搜索 App"均因此下架或被诉。
**这是产品级的一票否决，不是可以靠合规声明或免责条款绕开的实现细节。**

### 1.5 小结

原始路径的四个环节里，环节二在技术上已经断裂，环节三、四在法律上被否决。
但值得注意的是：**断裂的是"从哪里取数据"，不是"取到数据之后怎么处理"**。
解析、打分、排序、播放、下载这套下游能力完全成立——只要把上游换成合法且**主动提供结构化数据**的源。

## 2. 竞品与市场调研

### 2.1 谁在做这件事，怎么活下来的

| 产品 | 定位 | 规模 | 商业模式 |
|---|---|---|---|
| **JustWatch** | 全球最大的"去哪看"数据库 | 300+ 流媒体服务、60+ 国家 | 数据授权 + 跳转分成（CPA）+ 广告投放智能 |
| **Reelgood** | 统一流媒体导航与追剧 | 28.5 万部电影、7 万+ 剧集 | 向 Roku、微软、智能电视厂商、对冲基金授权数据 |
| **TMDB** | 社区维护的影视元数据库 | 免费 REST API | 非营利/社区，观看渠道数据由 JustWatch 提供 |
| **Watchmode** | 面向开发者的可看性 API | 200+ 服务，每日更新，含深链 | 免费额度 2500 次调用，之后按量付费 |

JustWatch 与 Reelgood 合计活跃用户超 2500 万。

**这组数据回答了一个关键问题**：用户"一次输入、不用挨个平台试"的痛点是真实且巨大的，
真实存在的商业公司靠**只做导航、不碰片源**活得很好。
换句话说，原始需求里最有价值的那部分，恰恰不依赖抓取播放地址。

### 2.2 Reelgood 的一个洞察

Reelgood 自己的数据研究指出：**88% 的电影不在 Netflix / Disney+ / HBO Max 上**。
主流订阅平台之外存在一条极长的尾巴——其中相当一部分是公有领域与自由许可作品，
它们**没有 DRM、没有签名 URL、允许直接下载**，而且几乎没有产品认真为它们做过好用的检索与播放体验。

这条长尾就是本方案的落点：不是"退而求其次"，而是一块被主流产品忽略、且**技术上唯一能完整交付"点开即播 + 离线下载"体验的内容集合**。

### 2.3 合法且能拿到真直链的源

| 源 | 内容 | 是否给结构化直链 | 本方案 |
|---|---|---|---|
| **Internet Archive** | 公有领域长片、动画、纪录片，约 18.5 万部影像 | ✅ Metadata API 逐文件给出格式/体积/时长/分辨率/md5/sha1 | ✅ 主力源 |
| **Wikimedia Commons** | PD / CC 影像 | ✅ imageinfo 给直链、时长、许可 | ✅ 补充源 |
| **Jellyfin / Plex** | **用户自己的**媒体库 | ✅ 原生 static 直链，支持 Range | ✅ 自有内容源 |
| **TMDB（JustWatch 数据）** | 正版可看渠道 | 只给落地页，不给文件地址 | ✅ 元数据 + 正版导流 |
| Tubi / Pluto TV / Kanopy | 正版免费（含广告） | ❌ 不提供下载，无公开直链 API | 通过 TMDB 渠道数据导流 |

**Internet Archive 这一条尤其关键**：它以 API 形式主动给出了盗版站爬虫拼命想逆向、却始终不稳定的那份数据——
逐文件的格式、分辨率、时长、体积、以及**校验和**。前面 §1.3 说的"解析播放地址"这件事，在这里不需要解析，上游直接给。

## 3. 需求本质：用户到底要什么

把原始需求剥掉实现方式，剩下四条真实诉求：

| # | 诉求 | 现状痛点 | 能否合法交付 |
|---|---|---|---|
| N1 | **一次输入，不用挨个平台搜** | 片源分散在十几个服务里 | ✅ 完全可以 |
| N2 | **直接告诉我哪个能看，别让我逐个点开试** | 搜索结果里大量死链、预告片、片段 | ✅ 完全可以，且这是本方案技术含量最高的部分 |
| N3 | **点开就播，不要跳转、注册、装播放器** | 跳转链路长 | ✅ 在无 DRM 源上完全可以；有 DRM 的只能深链跳转 |
| N4 | **能离线带走** | 出差/飞机/弱网 | ✅ 在允许下载的源上完全可以 |

N2 值得单独说：用户抱怨的从来不是"搜不到结果"，而是"结果里全是噪声"。
一个能**筛掉预告片、筛掉死链、筛掉浏览器放不出来的容器、并说明理由**的排序器，
才是这个产品真正的价值所在——而它与内容是否盗版完全无关，纯粹是工程质量问题。

## 4. 产品定义

**CineRoute 影路** —— 输入片名，聚合公有领域 / 自由许可 / 你自己的媒体库，
给出可解释排序的 Top5 可播片源，点开即播，勾选即离线下载；
对受版权保护的作品，只回答"去哪能合法看"。

产品边界写死在代码里，不是文档里的一句承诺：

- 适配器注册表（`src/adapters/registry.js`）是唯一的数据源入口，加源必须显式登记；
- 媒体代理与下载接口共用同一份**域名白名单**，白名单外的地址一律拒绝；
- 正版渠道数据只透传落地页链接，管线里没有任何从中提取文件地址的代码路径。

## 5. 技术架构

```
                    ┌──────────────── 适配器层（可插拔）─────────────────┐
                    │ Internet Archive   Wikimedia Commons              │
   输入片名 ──────▶ │ Jellyfin(自有库)   TMDB(元数据+正版渠道)          │
                    └───────────────────┬──────────────────────────────┘
                                        │ 并发 · 单源失败隔离 · 超时熔断
                                        ▼
                          ┌─────────── 编排 pipeline ───────────┐
                          │ 准入过滤（相似度/年份）              │
                          │ 去重（校验和优先，URL 兜底）         │
                          │ 参考片长（权威值 → 中位数兜底）      │
                          │ 第一趟预排名 → 选出前 12 个候选      │
                          │ 真实探测（HEAD / Range: bytes=0-1）  │
                          │ 第二趟重排 → Top5 + 备选            │
                          └───────────────┬─────────────────────┘
                                          ▼
                     Top5 直链 ──▶ <video> 同源代理播放
                              └──▶ 分块并发下载 + 断点续传 + 校验
```

### 5.1 六维可解释打分（满分 100）

| 维度 | 权重 | 判据 |
|---|---|---|
| **可播性** | 30 | 容器是否浏览器原生可播；是否支持 Range；是否 HTTPS；探测是否可达 |
| **清晰度** | 20 | height；缺失时由 format 名推断并打 0.85 折 |
| **完整度** | 18 | 时长 vs 参考片长；标题含预告/花絮关键词直接归零 |
| **码率** | 12 | bytes×8/时长，1.5–6 Mbps 为最优区间 |
| **来源可信** | 12 | 许可明确度（PD/CC0 > CC-BY > 未标注）+ 馆藏加权 |
| **人气** | 8 | 下载量对数归一 |

### 5.2 三个关键设计决策

**① 可播性既是最高权重，也是硬门槛。**
一个 4K 的 MKV 在浏览器里是黑屏，一个 480p 的 MP4 立刻出画面。对"点开就要看"的产品，后者才是好片源。
所以不可播容器直接被踢出 Top5，进入"可下载后本地播放"的备选区并附原因，而不是靠扣分让它自然沉底——
扣分挡不住一个 4K MKV 靠清晰度分挤进第一。

**② 两趟排名，把探测成本压到常数级。**
上游声称"这是个 mp4"不等于它能播：链接可能已失效、可能不支持 Range。
但对全部候选发探测请求代价太大。因此先用元数据预排名选出前 12，只探测这 12 个，再带真实结果重排。
最高权重维度因此建立在事实而非声明之上。

**③ 无权威片长时用候选时长中位数兜底。**
完整度维度需要参考片长来识别预告片。没有 TMDB key 时，取该作品所有候选片源时长的**中位数**——
归档站里正片副本通常多于预告片副本，中位数天然落在正片时长上。
实测：零 API key 情况下推定出 5754 秒（96 分钟），与真实片长一致，成功把 142 秒的预告片和 743 秒的花絮挡在 Top5 外。

### 5.3 安全边界

服务端的 `/media` 代理存在的理由是解决上游缺 CORS 头与明文 HTTP 混合内容两个播放障碍。
但一个"按 URL 参数转发请求"的接口，如果不加限制就是一个**开放代理**，可被用来探测内网与云元数据服务（SSRF）。

因此 `/media` 与 `/api/download` 共用同一份域名白名单，并已用例覆盖：
`169.254.169.254`、`127.0.0.1`、`10.x`、`192.168.x`、`[::1]`、`archive.org.evil.com`（后缀伪装）、
`file://`、`ftp://` 全部拒绝。

另一条边界在前端：片名与文件名都是**第三方归档站上的用户上传内容**。
前端全程用 `createElement` + `textContent` 构建 DOM，不做任何 `innerHTML` 字符串拼接——
否则一个恶意条目标题就能在本地页面里执行脚本。

## 6. 已验证的能力

50 个用例全部通过（`npm test`，无需联网、无需 API key）：

- **打分与排序**：可播性优先于清晰度（480p MP4 排在 1080p MKV 之前）、硬门槛、Range 扣分、明文 HTTP 扣分、中位数片长估计；
- **端到端管线**：用真实形状的上游响应夹具跑**真实解析代码路径**——Top5 排序正确、预告片/花絮被挡、非视频文件被过滤、多源结果合并、单源故障隔离；
- **下载器**：对着本地 HTTP 服务真下载——分块并发后逐字节一致、md5 校验通过、校验失败不交付、**断点续传只补未完成分块**、无 Range 时退化为单流；
- **安全**：SSRF 白名单、目录穿越、协议限制。

CLI 实测输出（离线夹具，零配置）：

## 8. 风险与边界

| 风险 | 应对 |
|---|---|
| 归档站条目的许可标注可能有误（用户上传时填错） | 许可未标注时"来源可信"维度只给 4/12 分；UI 展示原始许可字段与来源页链接，供用户自行核实 |
| 公有领域状态因司法辖区而异（美国 PD ≠ 全球 PD） | 文档明示；正版渠道按 `CINEROUTE_REGION` 分地区返回 |
| 上游 API 变更 | 适配器隔离，单源失败不影响其余源；每个适配器有独立夹具用例 |
| 用户把白名单改成任意域名 | 白名单是代码常量而非配置项，改动需要显式提交；`/media` 与下载共用同一份闸 |
| 抓取压力打扰上游 | 全局并发闸（默认 6）+ 指数退避 + 探测只覆盖前 12 个候选 |

**明确不做**：不解析任何受版权保护作品的播放地址；不集成盗版索引源；不实现 DRM 规避；
不提供"把正版平台的流转存到本地"的功能。这些边界写在代码结构里（白名单 + 适配器注册表），不只写在文档里。
